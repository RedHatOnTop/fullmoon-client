풀문 클라이언트는 두 조각이다 — 게임을 깔고 실행하는 런처, 그리고 게임 안에서 서버가 보낸 데이터를 그리는 mod. 이 사이트는 실제 소스 파일을 따라 걷는다. 파일 이름과 줄 수는 커밋 기준이고, 언제든 직접 열어 대조할 수 있다.

STRUCTURE  ║  두 조각, 하나의 계약

디렉터리 지도

전체 트리는 짧다. 제품 코드는 런처와 mod, 그리고 둘을 잇는 프로토콜 문서뿐이다.

fullmoon-client/
launcher/
├ src/ — React UI (screens, state, widgets)
├ src/core/bindings.ts — UI↔core 유일한 접점
└ src-tauri/ — Rust core (4,500줄, 19 모듈)
pinion-mod/
├ hud/ — HUD·설정 GUI·코스메틱
└ bridge/ — 서버 채널 클라이언트
docs/
└ BRIDGE.md — 프로토콜 스펙 (공개 계약)
.github/workflows/
└ ci · release · site — 빌드와 배포 전부 자동

계약이 먼저다

UI는 Rust core를 모른다. mod는 서버를 모른다. 둘 다 자기 옆 사람과의 계약만 안다 — bindings.ts(UI↔core)와 fullmoon:v1 채널(mod↔서버). 계약이 안정적이면 안쪽은 언제든 갈아끼운다. 실제로 UI는 mock core 위에서 먼저 완성됐고, Rust core가 나중에 같은 계약으로 갈아탔다.

숫자로 보는 규모

  • 37개 Tauri 명령 — 계약의 전부, commands.rs 한 파일에
  • 1개 채널 페이로드 — varint 프레임 + JSON 한 객체
  • 0개 외부 에셋 다운로드 — Mojang 원본만, SHA1 검증해서

읽는 순서

01

런처

bindings.ts 계약, Rust core의 설치 파이프라인, 계정 흐름. UI가 먼저 완성된 희한한 순서의 이야기.

 02

인게임 mod

HUD와 설정 GUI가 런처 디자인 언어를 미러링하는 방식, 워프 스크린이 ChestGUI를 대체한 과정.

 03

브리지 프로토콜

한 개의 커스텀 채널로 워프·스크린·텔레포트를 나르는 법. 위조를 전제한 설계가 왜 단순해지는지.

 04

신뢰와 배포

SHA256SUMS, 태그 빌드, 서명된 OTA. "이 exe가 이 커밋이다"를 성립시키는 장치들.
