# P9 Hallmark anti-slop audit

The six-axis critique covers warp from the map. Philosophy is 5 because the map still owns no
authority it did not have: it sends a route id the server published and renders the verdict the
server returned, with an explicit fallback for a reason the protocol does not define; hierarchy is 5
because the plane stays the subject and position, routes, the chosen route and the one action read as
four separate registers around it; execution is 5 because the surface was driven against live Paper
at 960×540 and 640×360 GUI px through hover, choice, accept, refusal and the window between request
and answer; specificity is 5 because every visible fact is measured, server-owned or arithmetic a
reader can redo from the raster; restraint is 5 because the phase adds one ring, one line of hint,
one status slot and one action, and the ring it adds is the ring the map already drew; variety is 4
because it deliberately reuses i3's spine-and-rail grammar rather than inventing a second one for a
screen that now acts.

Audit basis: the [Hallmark 58-gate slop test](https://raw.githubusercontent.com/Nutlope/hallmark/main/skills/hallmark/references/slop-test.md),
applied to native Minecraft GUI without claiming that DOM, CSS, SEO, browser navigation, or web hero
gates exist. Every applicable answer is **No**. Web-only gates are **N/A**. Gates 15, 17 and 46 are
answered anew: P8's map had no focusable widget, no tooltip and no request, and all three now exist.

Honesty notes.

`MapScreen` has no unit test and is not in the coverage gate, the same as P8 and for the same
reason: it is a draw-and-dispatch shell over `MapMarkers`, `MapViewport` and `WarpRoutes`, which are
gated at 100% line and branch. What the shell does is settled by the frames above, not by a test.

Gate 17 deviates from the stated 800–1000 ms hover convention and answers No anyway. The kit's
`Tooltip` ships no delay and no fade at all — its class doc says so and says why — and a marker
cannot take the keyboard, so the pair the gate compares does not exist here. The convention exists to
stop tooltips flickering as a pointer crosses dense targets; the hit radius is 2.5 cells, or 7.5 GUI
px, on a plane holding six markers, so the flicker it prevents does not arise. Nothing is
pointer-exclusive either: the rail publishes every route's name and coordinates unconditionally, so
the hint repeats a fact rather than being the only place it is said. If markers ever become dense or
focusable, the delay pair has to arrive with them.

Gate 26 is answered from the kit, not from a P9 frame. Every committed run clicks rail row 0 before
it touches the map, so no frame in this phase catches the action disabled; `State.live()`'s own doc
records that the gallery draws all eight and only the ones that still answer a click act.

`status.warn` — the amber that renders `서버 응답 대기 중` — has no declared contrast floor among the
nine checks in `design/generate.mjs`, though it measures 10.53:1 on the ground it is drawn over. That
is a gap in the generator, not a failure of this surface, and it is named here so the next phase that
touches `tokens.json` can close it rather than rediscover it.

One fixture was used and restored. The in-flight pair needed the server to hold an answer longer than
the rig's 1.6 s shutter, so `handleTpRequest`'s body was renamed and deferred by 80 ticks
(`1d8a2e6e66341836c56a8fe2ec659c03314151071cb1d7005a808cb83567c376`), then restored to the shipped
source (`db30e62c8d1bbed9ba75d87b099caa82055a4c9ce6656001c78cab7d055fc14c`, the value P6 and P7 also
recorded restoring to). Nothing was installed on the production Oracle host at any point in this
phase.

Result: **PASS — 58 gates answered; no applicable gate answered Yes.**
